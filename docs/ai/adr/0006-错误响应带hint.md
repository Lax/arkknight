# ADR-0006：错误响应带 `hint`，面向「去哪里改」

- **状态**：已接受
- **日期**：2026-10-09
- **关联**：`../arkknight-design.md` §17

## 背景

原错误响应形如 `{"error": "token 无效或缺失"}` —— 告诉了「什么错了」，但没告诉
「接下来做什么」。几个具体困境：

- 401 不知道 token 该配在哪个文件、哪个键，也不知道控制台侧怎么填
- `账号 ghost 不存在` 不知道当前有哪些账号（是不是 key 拼错了？）
- `uid "12ab" 不合法` 不知道 UID 该去哪里抄、留空会有什么后果
- `设备 redroid-x 不存在` 不知道已注册了哪些设备、`device add` 怎么写参数

用户视角：这些错误都需要**离开当前界面去查别处**，而报错本身不给出那条路。

## 决策

**所有错误响应带 `hint` 字段**，内容是「去哪里改」的具体可操作信息：

```json
{ "error": "<发生了什么>", "hint": "<怎么修>" }
```

401 额外带 `detail`（区分「未携带」与「已提供但不一致」）与 `config_path`（配置文件绝对路径）。

按错误类型分流 hint：

| 场景 | hint 内容 |
|---|---|
| 401 | `[server].token` 键名 + 配置文件路径 + 控制台侧填法 + URL 参数用法 |
| 实体不存在 | 当前已注册的 key/name 清单 + `add` 命令模板 |
| uid 格式错 | 去哪抄 UID + 留空的后果（跳过核验、doctor 告警串数据风险） |
| account_name 重复 | 匹配串唯一性规则（官服打码手机号 / B服昵称） |
| key/slug 非法 | 字符集与首字符规则 |
| 会话被占用 | drain 命令 + 「可能是重启残留」的说明 |
| 设备后端不可用 | 配置文件路径 + doctor 提示 |

前端 `api.ts` 把 `hint` 并入抛出的 `Error`，控制台直接展示。

## 备选与否决理由

- **只加 `hint` 一个字段，不加 `detail`/`config_path`**：更简洁，但「未携带」与
  「已提供但不一致」对用户的行动建议完全不同（一个是去填，一个是去核对），
  合并成一句会变得冗长。拆开更清晰。
- **用 i18n 错误码 + 前端映射文案**（如 `{"code":"AUTH_INVALID"}`）：更规范，
  前端可本地化。但当前控制台只中文、错误种类有限，引入码表增加维护面而收益不明显。
  若将来要多语言，再从现有 hint 反推码表不迟。
- **在错误里直接给可执行命令让用户粘贴**：`hint` 里已包含命令模板，但 API 场景下
  用户未必在终端前（如从控制台点按钮触发的 404）。所以 hint 描述「怎么改」，
  不假设用户位置。
- **写进日志而非响应**：用户看不到日志。

## 后果

✅ 报错自带出路：控制台里点一下按钮触发的错误，用户不必切到终端就能知道下一步。

⚠️ hint 是中文字符串，进响应体即进 API 契约 —— 变更文案算契约变更。
`account_json` 等响应体已结构化，错误体的 `hint` 目前**无稳定 schema**，
依赖它的前端代码需容错（`api.ts` 用 `data.hint` 可选取值）。

⚠️ 维护成本：新增错误类型时要同步想 hint 文案。已有测试
`不存在实体的报错列出已注册项` 与 `鉴权失败报错带hint与配置路径` 部分守着。
